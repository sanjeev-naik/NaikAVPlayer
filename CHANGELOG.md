## [Unreleased]

### Added

- **HDR → SDR Tone Mapping (`naikav::video::ToneMapper`):** HDR10, HDR10+, Dolby Vision (base layer) and HLG sources are now converted for SDR display instead of being truncated to 8 bits with their transfer curve intact. Decodes the PQ (SMPTE ST 2084) or HLG (ARIB STD-B67, including its OOTF) transfer function to linear light, rolls highlights off with the ITU-R BT.2390 EETF, converts BT.2020 → BT.709 in linear light with out-of-gamut colors desaturated toward their own luminance, and re-encodes with the BT.709 OETF. Source peak is read from mastering-display metadata when present; display peak defaults to the 100-nit SDR reference and is adjustable. LUT-driven and split across worker threads.
- **HDR tone mapping panel (`C` hotkey / controls-dock `[HDR]` button):** Reports the source's HDR standard and the live tone mapping status, and carries the HDR → SDR on/off toggle and the display-peak slider (50–1000 nits). Both settings persist to `player_settings.txt` (`hdr_tone_map_enabled`, `hdr_target_peak_nits`) and take effect on the next decoded frame.
- **HDR10+ and Dolby Vision dynamic metadata now drive the tone curve.** Both formats were detected and named in the HUD but every frame was mapped from one static peak, which is the thing dynamic metadata exists to avoid: a dark scene in a 4000-nit grade was rolled off as though it reached the grade's peak. The per-frame peak is now read from HDR10+ `maxscl` (SMPTE ST 2094-40) or the Dolby Vision RPU's L1 block and used as the source peak, capped by the mastering display but deliberately not by MaxCLL -- the two are written by different tools and disagree by small margins, so clamping would discard the finer figure on most frames. Raw per-frame values pump visibly, so the peak is smoothed within a shot and followed immediately across a cut (a jump of more than 1.5x), then quantised to 25 nits so the tone mapper's tables are not rebuilt for every one-nit wobble. Measured across a cut-heavy stretch of the HDR10+ clip the source peak tracked 700 -> 475 -> 725 -> 650 -> 350 nits, easing within shots and snapping at cuts. Reported honestly in the HUD and the HDR panel, and switchable from there; note that a hardware decoder may strip the per-frame metadata, in which case the panel says so rather than claiming a dynamic curve it did not get.
- **AVX2 path for the tone mapper.** The per-pixel loop is compiled twice and selected once at runtime via `__builtin_cpu_supports`, so the binary still runs on machines without AVX2 -- which building the whole player with `-mavx2` would not. At native 4K the conversion went from **77 ms to 62 ms per frame (about 20% off)**. FMA is deliberately not enabled with it: contracting the HLG OOTF's multiply-adds changed that path's rounding, and the two code paths are verified to produce byte-identical output for both PQ and HLG, which is worth more than the further 4 ms it offered. Set `NAIKAV_NO_AVX2=1` to force the baseline path.
- **Source-peak override in the HDR panel.** The peak the content was graded for is normally read from the file, and the panel now shows which value that came out to. Behind an "Override source peak" checkbox is a logarithmic 100–10000 nit slider for files whose metadata is wrong — the setting the tone mapper has always accepted (`HdrToneMapSettings::sourcePeakNits`) but that nothing could reach. Persists as `hdr_source_peak_nits`; 0 means "read it from the file".
- **Tone mapping status in the diagnostics HUD:** `ColorPipelineInfo::toneMapped` reports whether the pipeline actually converted the frame, shown as a read-only line beside the rest of the color information. The HUD reports the pipeline; the HDR panel changes it.

### Changed

- **Builds against old FFmpeg again (Raspberry Pi / Linux ARM64).** Linux ARM64 deliberately links the distro's system FFmpeg rather than the bundled one, because that is what carries the V4L2 M2M hardware decoding a Pi needs -- and those can be several major versions behind. The HDR pipeline had been written against the bundled FFmpeg 8.x with no version guards, so on a system FFmpeg 4.4 `VideoDecoder.cpp` alone produced 21 compile errors. All version-sensitive uses now go through `src/core/FFmpegCompat.hpp`, which is the single place any threshold is stated, and each degrades to the behaviour that predates the feature rather than failing: `AVPacket::opaque` seek-generation tagging (FFmpeg 6.0), `AVCodecParameters::coded_side_data` and `::framerate` (7.0), Dolby Vision frame side data (5.0) and its L1 level blocks (7.0), HDR10+ dynamic metadata (4.3), and the threaded swscale API (7.1). The affected files now compile cleanly against both FFmpeg 4.4 and 8.1.
- **The last FFmpeg 5.1-only dependencies are gone, so the floor is now 4.4.** Two pieces of pre-existing audio code kept the build from reaching an older FFmpeg regardless of the HDR guards: `LoudnessMeter.hpp` used the `AVChannelLayout` API (libavutil 57.24, FFmpeg 5.1) and `LoudnessPrescan.hpp` passed `const AVCodec**` to `av_find_best_stream()`, whose parameter only became const in FFmpeg 5.0. Both now go through `FFmpegCompat.hpp` -- `naikavSetFrameChannelLayout()` and `naikavDescribeDefaultChannelLayout()` wrap just the two operations the player performs, falling back to the `uint64_t` mask API, and `NaikavBestStreamCodec` picks the right pointer type. Verified functionally rather than by compilation alone: the legacy branch returns the same layout names as the modern one ("mono", "stereo", "2.1", "5.1", "7.1"). **The whole application -- all seven translation units -- now compiles with 0 errors against both FFmpeg 4.4 and 8.1**, so Ubuntu 22.04 ARM64 is supported alongside current Pi OS.
- **Legacy swscale path for older FFmpeg.** Where `sws_scale_frame()` and a public `SwsContext` are unavailable, the HDR unpack falls back to `sws_getCachedContext()` + `sws_setColorspaceDetails()` + `sws_scale()`. Single-threaded, so materially slower (95 ms vs ~27 ms on a 4K frame), but visually the same picture: compared over a tone-mapped 640x360 frame, 93.4% of bytes matched exactly, mean absolute difference 0.07 of 255, largest difference 11 on 8 bytes out of 691200. Define `NAIKAV_FORCE_LEGACY_SWS` to exercise this path on a machine whose FFmpeg is new enough for either.

### Fixed

- **4K HDR playback ran at 2-3 fps.** The two `sws_scale()` calls that bracketed the tone mapper ran single-threaded — `sws_getContext()` has no way to set a thread count, and swscale only slices a conversion across cores when driven through `sws_scale_frame()`. On a 3840x2160 HDR10+ source the unpack to RGB48 alone cost 95 ms/frame and the repack to YUV420P another 47 ms, against 70 ms for the tone mapping they existed to serve. The unpack is now built with `sws_alloc_context()` and threaded, its kernel is chosen by the direction of the resample (bilinear at native size, area average when downscaling, bicubic when upscaling), and the repack is gone entirely: the tone mapper already produces RGB24, so the renderer uploads that to an RGB streaming texture instead of converting it to YUV for the GPU to convert back. Measured end to end, per frame: native 4K 303 ms -> 82 ms (12 fps), 1080p 114 ms -> 31 ms (33 fps), 720p 17 ms (60 fps). 4K at full resolution still does not reach 24 fps on a 4-core machine.
- **A video pipeline that fell behind could never catch up.** Every decoded frame was tone mapped in full even when the master clock had already passed it — so on content too heavy to decode and convert in real time, the renderer discarded the frame on arrival and the time spent converting it pushed the *next* frame further behind. The result compounded: video drifted steadily away from audio instead of settling. Frames now more than 100 ms behind the clock are dropped before the conversion (`PlayerController::shouldDropLateFrame()`), letting the decoder — which is faster than real time on every format the player handles — race back into step; at most 8 in a row are dropped, so the picture keeps moving under sustained overload. Measured on a 3840x2160 59.94 fps 10-bit AV1 HDR10 clip with no hardware AV1 decoder available, where decode alone needs the whole CPU: audio/video drift went from **1.72 s and growing to 0.12-0.14 s and stable**. Only applies while actually playing — a paused frame and a seek catch-up are untouched.
- **4K HDR was tone mapped at full resolution regardless of window size.** Tone mapping costs strictly per output pixel, and the result is scaled to fit the window before anyone sees it, so a 3840x2160 frame shown in the default 1024x576 window did about seven times the work the letterbox blit then threw away. The HDR path now caps its target to the renderer's output size (`capToDisplaySize()`), preserving aspect ratio and never upscaling. Per frame on the same 4K HDR10+ source: 91 ms -> 14 ms in a 1024x576 window (11 -> 74 fps), 30 ms at 1920x1080 (34 fps), 24 ms at 1600x900 (41 fps). Full-screen 4K is unchanged, since there the window really does want every pixel. The SDR path is untouched — it still honours the resolution selector exactly.
- **A file that failed to open did so silently.** `Demuxer::open()` reported its failures on stderr only, and three of the four `openFile()` call sites discarded the `false` return -- the command line, drag-and-drop, and the native file picker. With no console attached in the MSVC build, a bad file simply left the welcome screen up, which is indistinguishable from the player being broken; a truncated download once cost real time being debugged as a player fault. The demuxer now keeps the reason (`av_strerror` on the open failure, or a plain description for a file with no readable streams or no playable ones), `PlayerController::getLastOpenError()` exposes it, and every call site surfaces it -- a toast for the three that were silent, and the typed-path dialog's existing "Load Error" popup now shows the reason rather than only "verify the file path". Verified against a non-media file: "Invalid data found when processing input".
- **Turning the diagnostics HUD on dropped the frame rate and made playback stutter.** The video thread holds `m_videoDecoderMutex` across `decodeNextFrame()` *and* `convertFrame()`, which on 4K HDR content is tens of milliseconds — and five of the read-only properties the HUD shows every rendered frame (`getColorInfo()`, `isVideoHardware()`, `getVideoPixelFormat()`, `getVideoWidth()`/`getVideoHeight()`) took that same mutex, so the render thread simply waited on the decoder. Modelled at a 27 ms conversion with five reads per frame, the UI thread blocked for a **median of 80 ms per frame against a 16.7 ms budget** — the HUD was costing several frames' worth of time to draw. Those accessors now use `try_lock` and fall back to the last known value when the decoder is busy: same model, **median 0.00 ms**, with 595 of 600 reads served from cache. They are display-only figures that rarely change, so a value one frame old cannot be seen.
- **Audio started before video was ready, and the gap never closed.** `play()` started the audio clock the instant it was called, while the video path was still opening its codec, allocating a hardware context, building the tone-mapping tables and decoding a first 4K frame. Measured on the 4K HDR10+ HEVC clip, the first frame reached the render queue **1.10 s after `play()`**, by which time the audio clock already read 1.18 s -- and because the demuxer is paced by audio consumption, video then received packets at real time and could never decode ahead to recover. Every frame measured over a second late for the rest of the file. `prerollVideo()` now holds the audio clock at the starting line until the video pipeline has its first frame (2 s ceiling, after which audio starts regardless so a file whose video never decodes still plays). Skipped when there is no audio, and when frames are already in hand -- resuming from a pause does not wait. The offset went from **+1.15 s to -0.31 s**, which is the healthy direction: frames now sit decoded slightly *ahead* of presentation instead of over a second behind it. The HEVC clip went from 2.7 fps to a rock-steady **24.0 fps against its 23.976 fps source**.
- **The audio packet queue held too little time to buffer a preroll.** Its 150-packet capacity is about three seconds of AAC but only ~125 ms of TrueHD, whose access units are under a millisecond each. With audio held for preroll the queue filled almost immediately, the demuxer blocked on it, and it then stopped delivering *video* packets too -- so the first video frame never arrived and the preroll could only ever time out (measured: audio queue 150/150, video queue 0). Raised to 2400 packets, which covers the preroll window even for the shortest packets in practice; read-ahead is still bounded by the 100-packet video queue.
- **Video lurched between 3 and 44 fps on content the machine can decode comfortably.** Two separate faults, both in how a late frame was judged. First, `shouldDropLateFrame()` compared a frame's timestamp against the master clock in absolute terms, but the demuxer is paced by audio consumption -- once the audio queue is full it stops reading, so a player whose video path is keeping up receives packets at real time and cannot decode ahead however many frames it discards. A file that starts its audio before the first video frame is ready therefore carries that startup offset forever, and every frame measures late. On the 4K HDR10+ HEVC clip video pts trailed the clock by a steady **1.15 s** while both advanced at 1.001 s per second -- nothing was falling behind -- yet the max-consecutive rule let exactly one frame in nine through: **23.976 / 9 = 2.7 fps**, on content this machine decodes at 60. Dropping is now gated on the video packet queue actually being backed up, which separates the two cases directly: measured 100/100 packets queued on the genuinely congested 4K60 AV1 clip, 0-6 of 100 on the HEVC one where the decoder was simply waiting for data. That clip went from **2.7 fps to ~20 fps** against its 23.976 fps source.
- **4K60 HDR flashed rather than played.** Software-decoded 4K60 AV1 (no hardware AV1 decoder on this machine) leaves little CPU for tone mapping, so frames overran their 16.7 ms budget, arrived late, and were dropped in bursts -- on-screen delivery swung between **10 and 44 fps with gaps up to 200 ms**, which reads as flashing rather than as a low frame rate. The tone-mapping target is now shrunk when the measured conversion overruns the frame budget and restored when it fits (`AdaptiveToneMapScale`), reacting within three frames and recovering over about two seconds so the picture does not visibly breathe. The same clip now holds **40-59 fps with gaps of 30-48 ms**. Content with headroom is untouched -- the 23.976 fps HEVC clip stays at full size. Turn it off with the HDR panel's "Adapt resolution to keep frame rate".
- **HDR metadata was ignored entirely on the hardware decode path.** Mastering-display luminance and MaxCLL normally reach the player as frame side data, put there by the decoder from the codec's SEI -- but a hardware decoder does not do that. QSV hands back frames with none at all, so an HDR file played on the GPU was tone mapped from the generic 1000-nit default rather than from what it actually declares. Two fallbacks now cover it: the stream header (`codecpar->coded_side_data`), which serves containers that keep a copy, and failing that a one-time software decode of a single frame at open (`Demuxer::probeHdrMetadata()`) to read the values straight out of the bitstream. The second is what Matroska needs -- it commonly stores no stream-level copy at all, so the 4K HDR10+ MKV had *nothing* to fall back on. Measured on that file played through `hevc_qsv`: frame metadata 0, stream metadata 0, probe recovers **4000 nits mastering / 683 MaxCLL**, and the tone mapper is configured with 683 instead of the 1000-nit default. Only runs for streams declaring an HDR transfer whose container offered nothing, so SDR files and well-populated containers pay nothing.
- **MaxCLL was ignored when choosing the peak to tone map from.** Only the mastering-display metadata was read, so a film delivered on a 4000-nit reference monitor was mapped from 4000 nits however dim its actual grade was — most of the tone curve's range went to brightness the content never uses, and the result came out dim. The HDR10+ test clip is a fair example: it declares a 4000-nit mastering display, but its own `MaxCLL` records that no pixel anywhere in it exceeds **683 nits**, so it was being mapped from a peak nearly six times higher than anything present. The two figures are now reconciled by `selectSourcePeakNits()`: MaxCLL is preferred, capped at the mastering peak (content cannot out-run the display it was graded on), with either used alone when the other is absent and the tone mapper's default left in place when the file carries neither.
- **Dragging the display-peak slider wrote the settings file and re-seeked on every frame of the drag.** `setHdrTargetPeakNits()` called `saveSettings()` and then `seek()` on each intermediate value, so one drag tore the decode pipeline down and refilled it dozens of times a second. The peak setters now only store — the decoder re-reads them for every frame it converts, so the picture already tracks the drag during playback — and the panel calls the new `persistHdrSettings()` on `IsItemDeactivatedAfterEdit()`, which writes to disk and re-decodes only when playback is paused and nothing else would.
- **The diagnostics HUD kept reporting tone mapping after a seek away from it.** `VideoDecoder::flush()` left `m_lastFrameToneMapped` describing the frame from before the seek, so the HUD and the HDR panel could claim an active conversion until the next frame was converted. Cleared on flush.
- **An HDR source that left its matrix unspecified was unpacked with BT.601 coefficients.** The BT.2020 coefficients used to be forced through `sws_setColorspaceDetails()`, which the dynamic swscale API no longer consults — it reads every colour property off the frames. Frames missing a `colorspace` or `color_primaries` tag are now explicitly labelled BT.2020 before the unpack, which a PQ or HLG transfer function implies in practice.

- **HDR content no longer renders dark and desaturated.** The frame conversion path accepted only 8-bit `YUV420P`/`NV12` on its zero-copy route and sent everything else — including all 10-bit PQ content — through `sws_scale` to 8-bit `YUV420P`, which resamples the bit depth but leaves the PQ curve applied. The diagnostics HUD reported "HDR Standard: HDR10 (PQ)" over the resulting uncorrected picture. 100-nit reference white was reaching the display at code 130 of 255; it now reaches it at 213.

## [1.0.0] - 2026-07-19

### Added

- **Multi-threaded Architecture:** Coordinates a demuxer thread, video decoder thread, audio callback thread, and main render loop using bounded thread-safe blocking queues to eliminate CPU spinning and ensure smooth backpressure handling.
- **Symmetric Seeking:** Instantaneous keyframe seek operations flushing queues and decoding pipelines, resolving in under 80ms.
- **Dynamic Hardware Fallback:** Platform-specific hardware-accelerated video decoding (D3D11VA, DXVA2, QSV, and CUVID on Windows; VAAPI, V4L2M2M, QSV, and CUVID on Linux) with automatic, runtime fallback to software H.264 decoding on initialization or decoding failure.
- **Audio-Video Synchronization:** Sub-10ms audio-to-video synchronization using sample-accurate audio clock reconstruction from PCM sample offsets, falling back to a steady-clock wall clock for video-only streams.
- **Dynamic Resolution Scaling:** Real-time playback scaling supporting original source resolution down to 360p, 480p, 720p, 1080p, 1440p, and 4K configurations on the fly via UI dropdown.
- **GPU-Mapped Planar YUV Upload:** High-performance direct upload of YUV 4:2:0 planar frame data to GPU-mapped texture memory (`SDL_PIXELFORMAT_IYUV`), bypassing expensive CPU color space conversion.
- **Software Volume Attenuation:** Linear audio gain attenuation with optimized memcpy/memset bypasses for muted (0%) and full (100%) volume states.
- **Loop Playback:** Automatic wraparound seek to start of file (0.0s) upon reaching end-of-file for continuous playback.
- **Native File Dialog:** Win32/GTK3/Portal integration via `nativefiledialog-extended` (NFD) for cross-platform file opening.
- **Diagnostics HUD & System Info:** UI overlay showing real-time statistics for queue depths, decode/render latency budgets, audio-video clock drift, and decoding mode (HW vs. SW).
- **ImGui Interface:** Sleek, translucent desktop user interface utilizing bundled custom Noto Sans typography.
- **Testing Framework:** Custom test suite featuring mock FFmpeg and SDL components, validating core player states and pipeline synchronization.
